# OnPoint Website Architecture ↔ Systems Book Sync Map (v2026-02-17r2)

This map is the **single source of truth for synchronization** between:
- Website IA (public + investor portal pages)
- Notion operating system (databases/pages)
- Systems Book (master narrative + procedures)

## Canonical coding standard (use everywhere)

**IDs:**
- **SB-xx-yy** = Systems Book section
- **WP-xx-yy** = Website page
- **NSB-…** = Notion record (Systems Book DB) *(stored as a Notion property, not in the title)*

**Version locking:** every exported file (DOCX/PDF/MD) must carry the same `Version_Lock` and be recorded in the registry before distribution.

## Sync rules (practical)

1. **Book is the narrative backbone** (process, governance, explanations).
2. **Website is the marketing + access layer** (concise, CTA-driven, investor-friendly).
3. **Notion is the operating layer** (tasks, status, owners, artifacts, logs).
4. When in conflict, **Canonical_Source** wins. If `Website+Book`, changes must be applied to both in the same commit.

## Registry-driven workflow (how you actually run it)

**A. When you edit a Book section:**
- Update the Systems Book (DOCX master) under its SB code
- Update the mapped Website page (if Sync_Rule requires Book→Website or 2-way)
- Update the Notion record (owner/status/links) and attach the new file export
- Increment version only when you produce a distributable set (e.g., CIM set, Systems Book release)

**B. When you edit Website IA:**
- If it affects any `SB-04-*` items, update both Website and Book and re-export the mapping CSV
